# Figma 节点导入 tldraw 方案

> 整理时间：2026-10-17

## 1. 目标

把 Figma 里的一个 section 导入到 tldraw 画布上，尽量还原原本的样子。

## 2. 整体链路

```
自建 Figma 插件
   │  读：读字段、转 JSON、补矢量和图片
   │  写：执行服务端推来的写入命令
   ▼  ⇅ WebSocket
应用后端（内置中转站）
   │  按用户和文件路由，双向转发
   ▼  ⇅ WebSocket（通过 SDK）
你的应用：转换层（纯函数）
   │  去默认值、归一化 → 渲染数据
   ▼
tldraw 自定义图形（ShapeUtil）
   │  component 里调用渲染组件
   ▼
渲染组件（按 node.type 分发的 React 组件）
```

一句话总结：**插件负责"读全、读对"，转换层负责"精简"，渲染层负责"画出来"。**

## 3. 和 Figma 通信：自建插件 + 后端中转

### 3.1 为什么用插件，而不是 REST API 或 MCP

- 插件以当前登录用户的身份直接读取文档，不需要 token，也没有接口限流
- 插件 API 能读到的数据比 REST API 更全，比如矢量路径、实例的覆盖信息、组件库里的主组件
- 交互方式很自然：在 Figma 里选中一个 section，就能推送到 tldraw

**限制：** 必须有人打开 Figma 并运行插件，所以不适合无人值守的批量导入。

### 3.2 中转站放进应用后端

插件和浏览器页面都只能主动连接别人，不能被别人连接，所以中间必须有一个服务端来转发消息。中转站直接做在应用后端里，**用户只需要安装插件，不用另外安装本地工具**。

```
Figma 插件（UI iframe 里的 WebSocket）  ⇄  应用后端（中转）  ⇄  应用前端（SDK）
                                                  ⇅
                                          服务端自己的写入任务
```

**为什么必须用 WebSocket：** 除了读取，还有**服务端往 Figma 写入**的需求。插件要一直保持连接，服务端才能随时把命令推过去。

**协议：**

1. 插件和应用前端都连上 `wss://你的域名`
2. 通过配对或登录，绑定到同一个"用户 + 文件"
3. 任何一方都可以发命令：`{ id, command, params }`
4. 执行方用同一个 `id` 返回结果；耗时长的任务中途可以发送进度消息

**SDK（给应用前端用）负责：** 连接、发送命令、按 `id` 等待结果、把分批的数据拼起来、处理超时和重连。

**实现时要注意：**

- **插件的网络**：插件主线程不能联网，WebSocket 要放在插件的 UI（iframe）里，再通过 `postMessage` 和主线程通信；manifest 的 `networkAccess` 里要声明后端域名
- **配对**：要知道哪个插件对应哪个用户的哪个画布。可以让画布显示配对码，用户在插件里输入；或者两边用同一个账号登录
- **识别文件**：用 `figma.fileKey`，只有私有插件能读到，需要在 manifest 里开启 `enablePrivatePluginApi`
- **在线状态**：后端要记录哪些插件在线、分别打开了哪个文件。插件不在线时，命令要立即报错，不要一直等待
- **连接稳定性**：加上心跳检测和自动重连，重连后重新上报自己打开的文件
- **大数据走 HTTP**：图片和大的快照用 HTTP 上传下载，WebSocket 只传命令、结果和通知
- **超时**：按数据量设置，不要用固定的短超时
- **多台机器部署**：WebSocket 连接会分散在不同机器上，需要用 Redis 这类工具在机器之间转发消息
- **数据经过服务器**：如果是公司内部的设计稿，要确认这样做是允许的

### 3.3 插件的命令设计

**不追求"把插件 API 透明地暴露出来"，原因有两个：**

1. **技术上做不到原样传输**：插件 API 里的节点是"活对象"，有 getter、异步方法、`figma.mixed` 这类特殊值和二进制数据，没法直接转成 JSON 发出去，总得有人决定读什么、怎么转换
2. **安全**：如果允许执行任意代码，本机任何能连上中转站的程序都能随意操作你打开的 Figma 文件

**读取命令：**

1. **`export_for_render`**：渲染的主流程，读取选中的节点或指定节点，输出原始快照
2. **通用的"读属性"命令**：传入节点 id 和属性名列表，返回转换好的 JSON。用于调试和探索，不用每次都改插件
3. **读取图片**：用 `figma.getImageByHash(hash).getBytesAsync()` 读取原始字节，分批发送
4. **导出 SVG／PNG**：用于复杂图标、兜底，以及缩小时使用的预览图

**要注意的一点：** 插件里的 `exportAsync({ format: "JSON_REST_V1" })` 导出的数据不包含矢量路径，需要另外通过插件 API 读取（见 4.1）。

**写入命令：**

- 同样只开放固定的命令，粒度类似"创建 frame""设置填充""替换文字""设置图片"
- 现在命令来自服务器，风险比本地更大，所以**不提供"执行任意脚本"的命令**

### 3.4 写入 Figma 的注意事项

- **字体**：修改 `.characters`、`.fontSize`、`.fontName` 这类会影响显示的文字属性之前，必须先调用 `figma.loadFontAsync`
- **撤销**：一批写入完成后调用 `figma.commitUndo()`，设计师按一次 Ctrl+Z 就能撤销整批改动
- **图片**：先用 `figma.createImage(bytes)` 拿到 hash，再设置成填充
- **设计师可能同时在编辑**：写入前确认目标节点还存在，不存在就返回明确的错误
- **防止重复执行**：每条命令带唯一的 `id`，插件对重复的 `id` 不再执行，避免断线重连后重复写入
- **让设计师知情**：插件界面上显示最近执行的写入记录，并提供一个"允许写入"的开关

## 4. 分层职责

### 4.1 插件层：读全、读对，不做精简

- **按节点类型维护字段白名单**：决定读哪些属性，用不到的就不读
- **把活对象转成 JSON**：处理 `figma.mixed` 这样的特殊值、二进制数据，以及需要异步读取的值
- **补齐 REST 格式里没有的数据**：
  - 矢量路径：`vectorPaths`、`fillGeometry`、`strokeGeometry`
  - 复杂图标：直接导出为 SVG
  - 文字分段样式：用 `getStyledTextSegments`
  - 图片：收集 hash，分批发送原始字节
- **输出一份完整、明确的原始快照**：即使是默认值也照样写出来

### 4.2 转换层：去默认值、归一化

- 写成**不依赖任何外部代码的纯 TS 函数**：输入原始快照，输出渲染数据
- 要做的事：
  - 删除隐藏图层（`visible: false`）
  - 坐标从绝对坐标换算成相对父级的坐标
  - 去掉默认值
  - 颜色转成 hex
  - 数字保留 1 到 2 位小数
  - 文字样式改成"区间"写法
  - 图片和复杂图标作为资源单独存放，节点里只放引用
- **共用一份 `defaults.ts`**：转换层用它来删除默认值，渲染器用它来补齐默认值，两边规则保证完全一致
- 默认值要按节点类型区分，例如描边位置：矩形默认是内描边，矢量线条默认是居中描边

**为什么"去默认值"放在这一层：**

1. "什么算默认值"是由渲染器决定的，规则只能维护一份
2. 规则会随着支持的节点类型增多而经常修改，改应用代码比改插件方便
3. 原始快照可以存成文件，不打开 Figma 也能反复跑转换、做回归测试
4. 排查问题时边界清楚：快照里没有某个值，是插件的问题；快照里有但渲染错了，是转换层或渲染层的问题

**留一条后路：** 如果数据太大导致超时，因为转换层是纯函数，可以直接打包进插件里执行，不需要重写。

### 4.3 渲染层：按节点类型分发的 React 组件

- 按 Figma 的**节点类型**拆分，而不是按"工具"拆分
- 写一个 `<FigmaNode>` 组件，根据 `node.type` 分发给对应的组件，然后递归渲染子节点
- 容器类（FRAME / SECTION / GROUP / INSTANCE）用 `div`，矢量和布尔运算类用 `svg`，文字单独处理
- 第一版全部用绝对定位，以后再考虑把 Auto Layout 转成 flex
- 搞不定的节点，用插件导出的图片来兜底

## 5. 接入 tldraw

### 5.1 先用做法 A：一个 section 对应一个图形

- 写一个 `figma-section` 自定义图形，在 `component` 里调用渲染组件
- 好处：已有的渲染代码全部复用，还原度高，实现最快
- 限制：在画布上只能整体选中、移动

### 5.2 以后再考虑做法 B：一个节点对应一个图形

- 等真的需要"在画布上单独编辑某个图层"时再做
- FRAME 继承 `BaseFrameLikeShapeUtil`，用 `getClipPath` 实现裁剪
- 代价：要处理坐标换算、旋转、层级顺序；节点很多时性能会明显下降
- 可以从 FRAME、TEXT 这些常用类型开始，逐步拆出去

### 5.3 注意事项

- 图形的 props 里只放这个图形自己要用的数据
- 渲染内容设置 `pointer-events: none`，避免抢走画布的选中和拖拽操作
- 事先决定缩放行为：要么整体等比缩放（CSS `scale`），要么禁止缩放
- 图片要存到自己的地方，或者存进 tldraw 的 asset 里
- 如果要用 tldraw 自带的导出功能，先验证 HTML 内容能否正常导出，不行就自己实现 `toSvg`

## 6. 渲染性能

按收益从高到低：

1. **缩小时换成图片**：缩放比例很小的时候切换成预先渲染好的图片，放大后再切回 DOM
2. **控制图形数量**：这也是先选做法 A 的原因
3. **屏幕外的不渲染**：确认自定义图形没有关掉 tldraw 默认的 culling
4. **避免重复渲染**：用 `React.memo`，并保证传入的数据引用不变
5. **少用费性能的特效**：拖动或缩放画布时，临时关掉模糊、阴影这类效果
6. **图片尺寸合适**：先缩到需要的尺寸再显示

**不做的事：**

- **不做数据去重**：存储和网络成本已经有其他方案解决，而去重对渲染压力没有帮助（屏幕上要画的东西一个都不会少）

## 7. 已知难点（还原度方面）

| 难点                   | 处理方式                           |
| ---------------------- | ---------------------------------- |
| 文字的字体、行高、换行 | 最难做到完全一致，需要逐步调整     |
| 内描边和外描边         | 用 box-shadow 或 SVG 来模拟        |
| 蒙版                   | 用 `clip-path` 或 SVG mask         |
| 布尔运算               | 直接用插件读到的路径，不要自己计算 |
| 阴影、模糊、混合模式   | 基本能对应到 CSS，但细节会有差异   |

## 8. 推进顺序

1. **最小验证**：在后端加上 WebSocket 中转，搭好插件，实现 `export_for_render`，导出一个包含图标和图片的真实 section，存成原始快照文件
2. **转换层和 `defaults.ts`**：只支持 FRAME、TEXT、RECTANGLE、VECTOR 这几种类型
3. **渲染组件和 `figma-section` 图形**：放进 tldraw，检查还原度和性能
4. **根据测试结果决定下一步**：优先补上还原度差距最大的那部分，或者加上缩小时切换成图片的功能
5. **写入 Figma**：先做"替换文字""设置填充"这类简单命令，跑通配对、在线状态、撤销和重复执行这几件事
6. **需要单独编辑图层时**：再逐步改成做法 B
