# 产品方向和计划：产品设计

> 相关：[模块说明](README.md) · [调研：可交互设计稿的手工编辑](probe-interactive-editing.md) · [技术实现](tech.md) · [施工计划](plan.md)
> 原始方案：`tmp/interactive-plan.md`（用户写的《Figma RN 方言：用代码表达设计稿》，`tmp/` 不进 git）。下面是 2026-10-30 评审和讨论之后的版本。

## 1. 目标（2026-10-30）

把 Figma 里历史沉淀的设计资产导进我们自研的 Skia 产品，让用户留在新产品里，以后不回 Figma（用户说明）：

| 谁             | 在我们这边做什么                                          | 主次                 |
| -------------- | --------------------------------------------------------- | -------------------- |
| agent          | 读懂设计稿的结构、数值、组件关系，按要求改对              | 主要场景（用户拍板） |
| 设计师         | 看稿，体验和 Figma 一样；手工改稿                         | 次要场景（用户拍板） |
| 导入（一次性） | 页面、组件库、变量、样式、图片导进来，画出来和 Figma 一样 | 前提                 |

为什么要把设计稿写成代码：Figma 的原始数据又长又散，模型很少见过；截图只能看长什么样，看不出结构和数值；agent 最擅长读写代码（原始方案 §1）。

## 3. 整体怎么运转（2026-10-30）

```
Figma 文件 ──插件导出（一次性）──▶ 快照 JSON ──生成代码──▶ 设计稿代码（真实数据，git 管理）
                                                              │   ▲
                                                 求值（每个节点  │   │ 补丁（画布上的改动
                                                 带源码位置）    ▼   │ 变成最小的源码改动）
                                                         画布 JSON（Skia 引擎）
agent ⇄ 设计稿代码；设计师 ⇄ 画布
```

代码长这样（原始方案 §4、§6.5 的写法，按 §5 的修正改过）：

```tsx
/** @figma frame 20:1 "Cart" · 标签：主线 */
export default (
  <View
    nodeId="20:1"
    name="Cart"
    style={{
      width: 390,
      flexDirection: 'column',
      gap: t.space.md,
      padding: 16,
    }}
  >
    <Header /> {/* 子块 20:5 */}
    <Button
      nodeId="20:900"
      variant="primary"
      size="md"
      fg-overrides={{ '10:4': { characters: '去结算' } }}
    />{' '}
    {/* 10:4 = Label */}
  </View>
);
```

原始方案里仍然成立的：树结构和 Figma 一一对应、每个节点带 id（原则 3）；Figma 里共享的才共享、复制的就展开（原则 4）；只需搬运的数据放资源文件（原则 6）；扩展部分用 `fg-` / `Fg.` 一眼可认（原则 7）；目录跟着 Figma 的页面、Section、顶层画框走（§5）；拆分规则和逐层阅读（§6、§8）；分类标签（§7）。原则 5"页面是标记"在 §7 有控制地放宽。

## 5. 方言要改的地方（2026-10-30，评审结论）

1. **覆盖按 id 写，不按名字。** Figma 的覆盖记录按 `I<实例 id>;<主组件里图层的 id>` 记，`apps/client/src/figma/components.ts` 也是这么对应的。key 写主组件里图层的 id，名字放注释给 agent 看。覆盖是页面的主体，原始方案 §4.2 要当核心设计。
2. **拆分要管组件库。** 页面折叠完实例以后很小，1000 行的阈值在页面上几乎碰不到。组件文件拆成"接口"（props、变体的联合类型，agent 主要读这个）和"每个变体的内部结构"，逐层阅读里加一层组件索引。
3. **几处"同名不同义"：**

   | RN 的写法                     | Figma 的实际意思                                                                                                           | 改法                                                                       |
   | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
   | 嵌套 `Text`                   | RN 会继承父 `Text` 的样式（原始方案 §1.3 说"没有继承"不对），正好对上 Figma 的"整段样式 + 分段覆盖表"                      | 只嵌套一层，子 `Text` 只写和整段不同的字段                                 |
   | `fontWeight: '600'`           | Figma 存的是字体样式名（"Semi Bold Italic"），数字字重会丢信息                                                             | `fg-fontStyle`                                                             |
   | `lineHeight`、`letterSpacing` | Figma 有百分比和像素两种单位，RN 只有像素                                                                                  | 带单位或用 `fg-`                                                           |
   | `transform: [{ rotate }]`     | Figma 旋转后的 x/y 是转过之后的左上角；RN 的 left/top 是没转之前的框，再绕中心转                                           | 用变换矩阵（同 figma-to-tldraw tech.md §4.2）                              |
   | 组写成 `<View>`               | Figma 的组没有自己的坐标系，组的框跟着子图层算                                                                             | `Fg.Group`                                                                 |
   | flexbox（Yoga）               | 旋转过的子图层按外接框占位，包裹内容时交叉轴不算"填充"的子图层，描边不占布局空间（figma-to-tldraw tech.md §13.2 的规则表） | 名字可以借，求值和预览必须用 `figma/editing/auto-layout.ts`，不能换成 Yoga |

4. **token 包括样式。** `tokens/` 要有颜色样式、文字样式、效果样式。插件现在只导出样式的名字和类型（`rest.styles`），没有值，要补导出。token 引用求值时只留 `$token`，值按节点所在的模式算（`figma/variables.ts` 的 `resolveVariable`），不能在求值时写死。

5. **折叠的矢量子树只读。** 原始方案 §6.2 第 3 步把图标折叠成一个 `Fg.Vector`，和"一一对应"冲突，也没说折叠后能不能改颜色。实例外能折叠的纯矢量组只有 155 个（0.7%），收益主要在组件文件里。要改就先展开。

## 6. 代码和画布的双向转换（2026-10-30）

**代码 → JSON（求值）。** 打开文件时把代码算成画布用的 JSON，就是现在引擎里的 `props.node`，现有的渲染、自动布局、组件、变量照用。每个节点记下自己在哪个文件、哪一行哪一列。

**画布改动 → 代码（补丁）。** 一次操作变成源码里最小的改动，不整个重新生成文件（会冲掉 agent 写的注释、顺序和拆分）：改间距只把 `gap: 12` 改成 `gap: 16`；新建图层插入一行 JSX；拖到别的 frame 就剪下、贴到另一处，可能跨文件。

"无感"要满足：

1. 不改就不变：代码 → JSON → 代码，文件一个字节都不变。
2. 只动改到的地方：一次操作在 git diff 里只出现相关的几行。补丁后用仓库的 oxfmt 格式化。
3. 结果对得上：补丁写回后重新求值，和画布上的 JSON 完全一样。
4. 拖动时只改 JSON，松手才写回代码，接在引擎"一次操作结束"的钩子上（`registerOperationCompleteHandler`）。
5. 改了绑 token 的值就解绑，代码里 `t.space.md` 换成 `16`，和 Figma 改变量的规则一样（`detachEdited`）；改 token 本身的值就改 tokens 文件。

**建议页面和子块文件直接解析、不执行**（原始方案 §11.1 的方案 A）。当时选"执行代码"的理由之一是不用自己解析模块关系；现在画布要改回代码，无论如何都得解析源码、知道每个节点在第几行。解析还有两个好处：不用在产品里执行 agent 写的任意代码，结果完全确定。要支持行为代码（§7）时再引入执行。

## 7. 可交互设计稿（2026-10-30，建议，用户未确认）

核心难点：带状态、循环、条件的设计稿还能不能在画布上手工改（用户提出）。调研见 [probe-interactive-editing.md](probe-interactive-editing.md)，结论：**能，前提是交互用编辑器认得的几种固定写法；任意代码只能显示、不能直接改。** 查到的产品都是这么划线的。

| 写法         | 例子                                    | 画布上怎么改                                   | 现有基础                                              |
| ------------ | --------------------------------------- | ---------------------------------------------- | ----------------------------------------------------- |
| 状态         | `state={{ tab: 'home', count: 1 }}`     | 顶上一个"当前状态"切换器                       | 变量和模式（`figma/variables.ts`）                    |
| 绑定         | `visible={$.count === 0}`               | 字段显示成"已绑定"；手改就解绑成写死的值       | `detachEdited`                                        |
| 按状态的样式 | 每个状态一份覆盖                        | 选中一个状态进入"录制"，改动只记在这个状态上   | 组件变体、覆盖记录                                    |
| 重复         | `<Fg.Repeat data={items}>`              | 改任何一项都是改模板；每项不同的地方只来自数据 | 实例引擎的"改主组件、同步到所有实例"                  |
| 条件显示     | 隐藏的图层                              | 在图层树里选中时临时显示出来编辑               | 隐藏的图层也建了图形（figma-to-tldraw tech.md §16.3） |
| 事件         | `onPress={set({ count: $.count + 1 })}` | 面板里列出动作，能改目标和值                   | 没有                                                  |
| 任意代码     | 自定义 hook、网络请求                   | 只显示；选中后"让 agent 改"                    | 没有                                                  |

原始方案 §15.4 的"回流"难题（设计师改了一张图，是想改所有状态、只改这个状态，还是只改这条数据）不用 LLM 猜，由编辑模式定：没选状态时改就是改所有状态；进入"录制某个状态"再改只记在这个状态上；改的字段绑着数据就是改数据。编辑和预览分开：画布上编辑时显示选定的状态，行为只在演示模式里跑。

## 8. 离开 Figma 必须自己补的（2026-10-30）

以前可以靠 Figma 事先画好的东西，现在都要自己算：

1. **矢量按几何数据画。** 现在矢量按 Figma 导出的 SVG 画，颜色写死在 SVG 里：改了填充画面不变，大部分隐藏的矢量没有 SVG（figma-to-tldraw tech.md §21.9）。导入时要导出矢量的路径数据，自己画、自己算布尔运算。这也是可交互和画布编辑的前提。
2. **图片滤镜自己算**（figma-to-tldraw tech.md §22 在做）。
3. **导入整份文件和团队库。** 插件现在一个用例、一个 section 手动导出；迁移要导整份文件的所有页面，还有跨文件的组件库和变量库，引用要对得上。
4. **样式体系。** 47% 的节点用了样式，我们还没有样式。
5. **代码的存储。** 现在用例从文件读，`/import` 存在浏览器的 IndexedDB，服务端只有登录。
6. **Figma 算好的字段会过时。** `absoluteBoundingBox`、`absoluteRenderBounds` 编辑后不准，要么自己重算，要么不存。
7. **和 Figma 一样的编辑体验还缺的：** 矢量编辑（钢笔）、换行和网格自动布局、评论、多人协作、整份大文件的性能（Untitled UI 的"组件"页 11892 个图形，打开 5.5 秒）。

## 9. 待定的问题

1. 交互的分界线：只用 §7 那几种写法，任意代码画布上只读、交给 agent？（建议：是）
2. 迁移期间设计师还会不会继续在 Figma 里改？会的话同一份文件要能多次导入，还要和我们这边的修改合并。
3. 代码存在哪：每份设计稿一个 git repo？服务端怎么存、agent 怎么访问？
4. 方言的运行时、生成代码和求值放哪：新的 `packages/*`（属于架构改动）。
5. `fg-` 扩展属性的名字：沿用 Figma 插件 API 的名字（语义精确），还是自己定（原始方案 §14）。
6. 拆分阈值（1000 / 600 / 100 行）用真实文件调。

## 10. 范围与非目标

**范围：**§1～§8。

**非目标：**写回 Figma、和 Figma 同步；在真实 React Native 或网页里运行设计稿代码（方言不是能上线的代码，原始方案 §15.6 第 3 条）；在画布上直接改任意代码（§7）。

## 11. 成功标准

1. 一份真实 Figma 文件整份导入，组件库和变量库的引用都连上，每页和 Figma 截图的差异 < 1%。
2. 快照 → 代码 → 求值，结果和快照逐字段一致，画出来逐像素一样。
3. 画布上的每种编辑操作，在 git diff 里只改相关的几行；不改就不变。
4. 同样的修改任务，agent 拿代码比拿原始 JSON 改对的更多、花的 token 更少（原始方案 §13 第 3 条）。
5. 用 §7 的写法写的交互稿，演示模式里能点；三种编辑模式的改动都生成对的补丁。
