# 调研：图片的 7 种调整能不能在我们的画布里画得和 Figma 一样？

> 2026-10-30，Figma 桌面版，Node 26.12.1，macOS 27.0.1
> 起因：做填充编辑弹窗的滑块（tech.md §22），滑块一拖就没有 Figma 渲染好的成品图了（§6.8）。用户问「这个问题有什么办法可以解决」，又问「是不是可以用 computer use 对一些特别的用例来实际操作……再实际截图测量效果」。
> 这份文档只回答可行性，不做设计。结论落地后写进 [技术实现](tech.md) §22。

## 1. 结论

**能，而且几乎一样。7 种调整都是"逐像素"的颜色映射：同一个颜色进去，出来的颜色总是一样，和周围的像素、整张图的明暗都无关。所以不用知道公式，让 Figma 给一张色表图套上每一档、导出来，网页里按颜色查表就行。**

| 调整                                | 逐像素 | 能拆成三个通道各一条曲线 | 色表实时画 vs Figma 成品图（`image-filter/*` 用例，最大差 / 差 3 级以上的像素） | 档位之间插值 vs Figma（平均 / 最大） |
| ----------------------------------- | ------ | ------------------------ | ------------------------------------------------------------------------------- | ------------------------------------ |
| 曝光                                | ✅     | ❌                       | 5 / 0.03%                                                                       | 0.33 / 7（0.37）                     |
| 对比度                              | ✅     | ❌                       | 4 / 0.04%                                                                       | 0.17 / 9（-0.63）                    |
| 饱和度                              | ✅     | ❌                       | 21 / 0.16%                                                                      | 0.12 / 2（0.12）                     |
| 色温                                | ✅     | ❌                       | 9 / 0.06%                                                                       | 0.15 / 14（0.84）                    |
| 色调                                | ✅     | ❌                       | 15 / 0.32%                                                                      | 0.25 / 15（-0.27）                   |
| 高光                                | ✅     | ❌                       | 5 / 0.03%                                                                       | 0.12 / 1（0.55）                     |
| 阴影                                | ✅     | ❌                       | 4 / 0.01%                                                                       | 0.07 / 1（-0.08）                    |
| 5 种叠加（`image-filter/combined`） | —      | —                        | 13 / 4.1%                                                                       | —                                    |

数字都是 0～255 的色阶。"差 3 级以上"按整张截图的像素算。没调整时同样这些用例差 3 级以上的像素有 27%～63%。

- **几种调整一起开时，Figma 按固定顺序一个接一个算**：色调 → 色温 → 对比度 → 高光 → 阴影 → 曝光 → 饱和度（§3.6）。按这个顺序一张张查表，7 种全开时平均差 0.83 级。
- **公式只推出来一部分**：饱和度往低调时 §6.8 的公式是准的，调到 +1 时加上"不超出色域"也准，+0.5 对不上；其余 6 种试了三种"先改亮度再处理颜色"的模型，平均差 0.5～14 级（§3.7）。所以用色表，不用公式。
- **代价是数据量**：每张色表 64 × 64 × 64 种颜色，169 张 PNG 共 15 MB。git 仓库才 4 MB，色表不进 git，和 `cases/` 一样放在根目录 `filter-luts/`，用脚本从插件导出的 zip 导入（tech.md §22.3）。
- **Figma 导出偶尔是空白的**：第一次跑 167 张里有 22 张整张透明，看起来是图片还没准备好就导出了。插件改成导完在界面里解码检查，空白就等 0.3 秒重导（§3.1）。
- 已经做进画布，做法见 [tech.md §22.3](tech.md)。

## 2. 怎么测的

**不猜公式，让 Figma 自己算，我们量结果。** 插件加了第 4 步"量图片滤镜"（`apps/figma-plugin/code.js` 的 `measureFilters`，`ui.html` 的 `makeCube` / `makeContext` / `measureJobs`）：界面里画两张图，交给 Figma，按一张清单逐个套上滤镜、导出 PNG，最后打成 `figma-filter-probe-<时间>.zip`。导出的做法和 §6.8 烤成品图一样（`bakeFilteredImage`：临时建一个和图片一样大的矩形，1 倍导出，导完删掉），不动任何页面。

两张图：

| 图             | 内容                                                                                                                                       | 用来回答                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 色表 `cube`    | 512 × 512，64 × 64 × 64 种颜色：分 8 × 8 格，第 b 格是蓝 = b 的那一层，格子里横着是红、竖着是绿；每个通道的第 i 档是 `round(i × 255 / 63)` | 每种颜色进去出来是什么                                                                                           |
| 场景 `context` | 512 × 256，左半黑底、右半白底，两边各放两块 64 × 64 的色块：灰（第 32 档，130）和橙（第 50、20、10 档，即 202, 81, 40）                    | 同一个颜色换了周围的颜色，结果变不变（是不是"逐像素"）；和色表里同一个颜色比，看结果和整张图的明暗分布有没有关系 |

清单（第一次 167 张，第二次 202 张）：

- 两张图各导一张不加滤镜的，确认 Figma 导入、导出不改颜色。
- 色表：7 种滤镜各取 24 档：-1～1 每 0.1 一档，0 附近变化快，再加 ±0.05、±0.15（第二次加的），不含 0，168 张。值是插件 API 的值，也就是 Figma 界面滑块的 -100～100 除以 100（对比度存进 REST 数据时再乘 0.3，见 tech.md §6.8）。
- 场景：7 种滤镜各取 -1 和 1，14 张。
- 色表上叠几种滤镜，11 张，用来找 Figma 先算哪个后算哪个（`COMBOS`）。
- 7 种滤镜各取一个不在档位上的值（`OFF_GRID`，如曝光 0.37），用来量档位之间插值准不准（第二次加的）。

导出时每张图都在插件界面里解码检查一遍（`isOpaque`），整张透明就等 0.3 秒重导，最多 10 次（§3.1）。插件第 4 步在 Figma 里跑一次约 30 秒。分析脚本是一次性的，放在会话的临时目录，没进仓库；用到的算法都写在下面。

量颜色用导出的 PNG，不用截屏：截屏会套显示器的色彩配置，Retina 下还会缩放，误差比要量的差别还大。computer use 只用来在 Figma 里点插件、点按钮、保存 zip。

判定标准：

- **逐像素**：场景图里黑底和白底上同一个色块，每个像素差不超过 1，并且和色表里同一个颜色差不超过 1。
- **能还原**：用量出来的数据在网页里算一遍，和 Figma 导出的图逐像素比，记下最大差和平均差。

## 3. 逐项结果

### 3.1 导出可靠性

第一次（2026-10-30 10:42）：167 张里 22 张整张透明（不加滤镜的两张、`cube/exposure/0.4`、场景图里 8 张……），其余都完整，没有"画了一半"的。说明 `exportAsync` 有时在图片还没准备好时就返回了。插件加了检查和重试以后，第二、三次都没有空白（第三次 202 张全部不透明）。不加滤镜的色表导出来和输入逐像素相同（最大差 0），说明导入、导出不改颜色。

> §6.8 烤成品图用的是同一个 `bakeFilteredImage`，也可能偶尔烤出空白图。这次没去查已有用例里的成品图，记在 tech.md 风险表。

### 3.2 是不是逐像素

14 张场景图（7 种 × ±1）里，黑底和白底上的同一块颜色，内部每个像素都一样（差 0），和色表里同一个颜色也一样（差 0）。高光、阴影也是这样，Figma 没有参考周围像素，也没有按整张图的明暗分布调整。

### 3.3 能不能按通道拆开

固定一个通道的输入、改另外两个通道，看这个通道的输出变不变：7 种都变，最大的是曝光 +1（253 级）。色温、色调连灰色都会变成彩色（本来就该这样）。曝光、对比度、饱和度、高光、阴影都保持灰色是灰色。所以每种调整都要一张三维的表（三个通道一起查），不能用三条一维曲线。

### 3.4 色表要多细

只保留每 3 档、每 7 档、每 9 档（22³、10³、8³）的格点，三线性插值后和全部 64³ 个测量点比：

| 色表 | 平均差     | 最大差               | 差 2 级以上 |
| ---- | ---------- | -------------------- | ----------- |
| 22³  | 0.10～0.39 | 8～26（饱和度 157）  | 0.4%～2.6%  |
| 10³  | 0.34～1.31 | 14～39（饱和度 171） | 3.2%～10%   |
| 8³   | 0.47～1.84 | 15～45（饱和度 172） | 4.8%～14%   |

误差集中在变化陡的地方（曝光把暗部提亮、饱和度碰到色域边上会拐弯）。用全部 64³，格点之间的误差在 §3.8 的端到端对比里一起算进去了。

### 3.5 档位之间插值

Figma 的滑块步长是 0.01，我们只量了 24 档，中间的值把两边两张表的结果按距离混合。第二次导出的 7 个不在档位上的值和预测比：平均差 0.07～0.33 级，最大 1～15 级，差 3 级以上的像素 0%～1.4%（数字见 §1 表）。第一次量时用隔一档预测中间一档（间距 0.2）试过，0 附近的误差最大（曝光 ±0.1 平均 2.5 级、最大 49 级），所以第二次在 0 附近补了 ±0.05、±0.15。

### 3.6 叠加的顺序

每对滤镜试两种顺序（三种以上试全部排列），看哪种顺序一张张查表最接近 Figma：

| 组合                       | 对的顺序        | 平均差 / 最大差 | 反过来的平均差 |
| -------------------------- | --------------- | --------------- | -------------- |
| 曝光 + 对比度              | 对比度 → 曝光   | 0.19 / 2        | 5.73           |
| 对比度 + 饱和度            | 对比度 → 饱和度 | 0.23 / 7        | 1.67           |
| 饱和度 + 色温              | 色温 → 饱和度   | 0.25 / 15       | 4.98           |
| 色温 + 色调                | 色调 → 色温     | 0.27 / 10       | 1.34           |
| 曝光 + 色温                | 色温 → 曝光     | 0.19 / 2        | 9.97           |
| 高光 + 阴影                | 两种一样        | 0 / 0           | 0              |
| 曝光 + 高光                | 高光 → 曝光     | 0.10 / 3        | 7.18           |
| 对比度 + 阴影（-0.5）      | 对比度 → 阴影   | 0.22 / 5        | 0.39           |
| 曝光 + 饱和度（都是 -0.5） | 曝光 → 饱和度   | 0.23 / 1        | 3.52           |

合起来是 **色调 → 色温 → 对比度 → 高光 → 阴影 → 曝光 → 饱和度**。5 种叠加（`image-filter/combined` 的值）按这个顺序平均差 1.04 级、最大 13 级；7 种全开（都是 0.5）平均差 0.83 级、最大 14 级。7 种全开时把阴影挪到曝光后面平均差变成 3.09，把曝光挪到最前面变成 11.9，所以顺序是对的。剩下的误差主要是因为每张表的结果都存成了 0～255 的整数，Figma 在中间步骤大概保留了小数。

### 3.7 公式推出来多少

- **饱和度**：先在线性光下（2.2 次方）算亮度 `Y`，结果 `= Y + k × (原色 - Y)`。往低调时 `k = 1 + 饱和度`，-1、-0.5 最大差 1 级（取整误差）。往高调时颜色会被推出色域，Figma 只推到色域边上：`k = min(1 + 饱和度, 让每个通道都留在 0～1 里的最大 k)`，+1 时最大差 1 级；但 +0.5 平均差 8.5 级，说明往高调时滑块和 `k` 不是直线关系，没再追。
- **曝光、对比度、高光、阴影**：用灰色的变化当亮度曲线，试了"按亮度比例缩放颜色、出色域就往灰拉""保持颜色和亮度的差、出色域就往灰拉""三个通道各自过曲线"三种模型，平均差最好的也有 0.5～14 级，最大差几十到两百多级。
- 同一个亮度的颜色，调完以后亮度也不一样（曝光 +1 时相差 0.33），说明不是单纯的"改亮度"。

再推下去要花很多时间，而且未必能推准，所以用色表。

## 4. 对设计的建议

1. 用色表实时画，Figma 烤好的成品图还在时优先用成品图（完全一样）。已做，见 tech.md §22.3。
2. 色表用 64³ 全量，不缩小：22³ 时变化陡的地方最大差 18～26 级。
3. 色表不进 git，跟 `cases/` 一样从插件导出的 zip 导入。Figma 改了算法时，重跑插件第 4 步、重新导入即可。
4. 以后要更准：三个都拉到头的叠加误差最大，可以让插件直接量常用的组合；或者等哪天要推公式时，这份数据就是现成的标准答案。
