# 设计稿方言：产品设计

> 相关：[模块说明](README.md) · [技术实现](tech.md) · [施工计划](plan.md) · [验证方案](verification.md)
> 上层的方向和决定见 [产品方向](../product-direction/README.md)。原始方案：`tmp/interactive-plan.md`（用户写的《Figma RN 方言：用代码表达设计稿》，`tmp/` 不进 git）。

## 1. 要解决的问题（2026-10-31）

产品方向已经定了：设计稿以**代码**为准，agent 读写代码是主要场景，设计师在画布上看稿、改稿是次要场景（[产品方向 product.md §2](../product-direction/product.md#2-已经定下的事2026-10-30)，用户拍板）。现在手里的设计稿都是 Figma 插件导出的快照（`cases/*/snapshot.json`），又长又散：Untitled UI 一页的 `snapshot.json` 40 MB 左右，agent 读不动，也看不出哪些是组件、哪些是覆盖、哪些值绑了样式。

这个模块做路线的第 3 步：**把快照变成方言代码 repo**，一个 Figma 文件一个 repo。用户追加（2026-10-31）：「现在把 figma 数据转成 RN 方言这个事项详细展开写成 feature doc」。

这一步只管"变成代码"和"检查变得对不对"。代码画到画布上、画布改动写回代码是路线第 4、5 步，以后在这个模块里接着写。

## 2. 怎么用（2026-10-31）

```
cd apps/client
npx tsx scripts/dialect.ts import [用例目录片段] [--out ../../designs]
npx tsx scripts/dialect.ts check ../../designs/<文件名>
```

- `import`：按 `cases/index.json` 把用例分到各自的 Figma 文件，每个文件生成一个 repo，默认放在仓库根目录的 `designs/<文件名>/`（不进 git，和 `cases/` 一样）。不给目录片段就生成全部。打印每个文件的页面数、组件数、文件数、行数、原样写出的字段、连不上主组件的实例。
- `check`：解析 repo 里的代码，变回快照，和原来的快照逐字段比，再跑 `tsc --noEmit`。不一样的地方列出用例、node id、字段和两边的值。agent 改完代码也跑它，检查写法对不对（那时候没有原快照可比，只做解析和类型检查）。

## 3. 生成的代码长什么样（2026-10-31）

agent 先读 `AGENTS.md` 和目录，再按需打开具体文件：

1. `pages/<页>/_index.md`：这一页有哪些屏幕，每个多大、多少节点、用了哪些组件。
2. `pages/<页>/<屏幕>/index.tsx`：屏幕的结构。
3. 太长的屏幕拆出来的子块。
4. `components/_index.md` → 组件的接口 `index.ts` → 结构 `component.tsx`。
5. `tokens/index.ts`：样式和变量。
6. `assets/`：图片、矢量，基本不用读。

一个屏幕文件的样子（细节见 [tech.md](tech.md) §3～§9）：

```tsx
/** @figma frame 3:1 "Settings" · 页面 Dashboards · 1468 个节点，本文件 42 个 */
import { Button } from '../../../components/button.10-1';
import { Fg, Text, View } from '../../../dialect';
import { t } from '../../../tokens';
import Header from './header.3-20';

export default function Settings() {
  return (
    <View
      nodeId="3:1"
      name="Settings"
      style={{
        position: 'absolute',
        left: 0,
        top: 0,
        width: 1440,
        flexDirection: 'column',
        alignItems: 'flex-start',
        justifyContent: 'flex-start',
        gap: 32,
        padding: 32,
        overflow: 'hidden',
        backgroundColor: t.fill['Base/White'],
      }}
    >
      <Header />
      <Text
        nodeId="3:40"
        style={{ alignSelf: 'stretch', color: '#101828' }}
        fg-textStyle={t.text['Display xs/Semibold']}
      >
        个人资料
      </Text>
      <Button
        nodeId="3:41"
        hierarchy="Primary"
        size="md"
        fg-overrides={{
          '10:4': { children: '保存' }, // Label
        }}
      />
    </View>
  );
}
```

读法：`View`、`Text`、`style` 里的键和 React Native 同名同义；`fg-` 开头的是 Figma 独有的，名字就是 Figma 导出数据里的字段名；`<Button>` 是组件实例，只写变体和覆盖；`t.fill['Base/White']` 是 Figma 里绑定的样式；宽度只写了固定的那些，包裹内容的不写。

## 4. 方言的规矩（2026-10-31）

原始方案的原则仍然成立（同名同义、无损、树和 Figma 一一对应、共享的才共享、页面是标记、只需搬运的放资源、扩展一眼可认），按产品方向的修正改过（[产品方向 product.md §5](../product-direction/product.md#5-方言要改的地方2026-10-30评审结论)）。这次展开设计时又定了几条（建议，用户未确认）：

1. **只写意图，不写结果。** 设计师定的数字（固定宽、间距、绝对定位的位置）写进代码；Figma 算出来的（包裹内容的尺寸、自动布局里子图层的位置、文字框大小、组的框）不写，打开时由我们的排版引擎重算。agent 改了间距，周围自动重排，代码里不会留下过时的坐标。见 tech.md §2。
2. **`fg-` 后面就是 Figma 导出数据里的字段名，取值也照写。** 不另起一套名字。还没专门设计写法的字段也按这条原样写出来，不会被悄悄丢掉。见 tech.md §3.1、§11。
3. **覆盖按主组件里图层的 id 写，值的写法和元素上一模一样。** 名字写在注释里。见 tech.md §8.3。
4. **样式、变量的 key 就是 Figma 里的名字**：`t.fill['Primary/500']`。见 tech.md §9。
5. **组件分成接口和结构两个文件**，agent 用组件时只读接口。见 tech.md §8.1。

## 5. 真实数据定下的重点（2026-10-31 实测）

203 个用例（88 个真实页面，6 套社区稿子）的字段统计，方法见 tech.md §15：

| 发现                                                                                   | 定下的事                                                      |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 页面上 22810 个节点，69% 在自动布局里，22% 是绝对定位，9% 在组里                       | 自动布局和绝对定位 + 约束都是主体，组要专门处理（tech.md §4） |
| 宽：包裹 6770、固定 5159、填充 4329；高：包裹 10769、固定 5297                         | 一半以上的尺寸是算出来的，"只写意图"省掉很多数字              |
| 实例的属性：变体 14993 个，文字 116、布尔 76；覆盖里改文字内容 1158 处、改尺寸 1439 处 | 页面文案几乎都在覆盖里，覆盖的写法决定好不好读                |
| 6 套稿子 203 个样式，每个样式的所有用处取值都一样                                      | 样式的值从图层反推，不用改插件（tech.md §9.1）                |
| 主组件按文件去重后 297 个、24134 个节点，是页面上实例外节点（6223）的 4 倍左右         | 组件库是体积的大头，要拆接口和结构；不是原来说的 10 倍        |
| 11% 的颜色不是整 8 位                                                                  | 这些不能写成十六进制（tech.md §5.1）                          |
| 1555 个组里 97% 的框等于子图层框的并集                                                 | 组的框可以不写（tech.md §4.4）                                |
| 旋转 328、镜像 48、分段样式文字 138、蒙版 12、换行自动布局 5                           | 少，但都要写得出、变得回                                      |

## 7. 范围与非目标

**范围：**快照 → 方言 repo 的生成器；检查用的反方向（解析、展开实例、变回快照、逐字段比）；生成 repo 里的 AGENTS.md、目录、类型定义；字段统计脚本。

**非目标：**

- 把方言代码画到画布上、画布改动写回代码（路线第 4、5 步）。
- 写回 Figma（产品方向已定不做）。
- 交互写法（产品方向 product.md §7）。
- 改插件：样式的值从图层反推；矢量的路径数据、整份文件导出是路线第 1 步。
- 分类标签（主线 / 探索 / 标注）、给默认图层名起别名、相似结构的提示。
- 多次导入同一个文件、和我们这边的修改合并。
- 证明 agent 读代码比读 JSON 好（路线第 6 步）。

## 8. 成功标准

1. `import` 对 6 套真实稿子和全部合成用例都能生成 repo，没有报错；原样写出的字段列在报告里。
2. 203 个用例"快照 → 代码 → 快照"逐字段零差别（按 tech.md §13.2 的定义）。
3. 生成的每个 repo `tsc --noEmit` 零错误；改一个变体名成不存在的值，tsc 报错。
4. 同样的输入生成两次，文件逐字节一样；再跑一遍 oxfmt，文件不变。
5. 阶段 0 测出整页重排后的还原度，和现在（203 个用例平均 0.09%、全部 < 1%）的差别写进验证结果，用户认可。
6. 用户看过手写样例和生成结果里的几个屏幕、组件文件，认可写法。
