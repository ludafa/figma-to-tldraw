分析已 staged 的改动，为它写一条符合 Conventional Commits 规范的 commit message 并提交。

本仓库不使用 changesets（三个包都是 private app，不发 registry），所以这条命令**只负责把已暂存的改动干净地提交进历史**——不生成 changeset、不动版本号。

步骤：

1. 运行 `git status` 和 `git diff --staged --stat` 看清暂存了什么。
   - 若暂存区为空：用 `git status` 把未暂存 / 未跟踪的改动列给我，等我确认要提交哪些，**不要自作主张 `git add` 全部**。
2. 看清改动落在哪些包 / 目录，据此确定 commit 的 type 与 scope：
   - type：`feat` 新功能 · `fix` 修 bug · `docs` 文档 · `refactor` 重构 · `chore` 杂务 · `test` 测试 · `build` 构建 · `ci` CI。
   - scope：受影响的包或模块，如 `server` / `client` / `docs`；跨多包或全局改动可省略 scope。
   - **一次 commit 只做一件事。** 若暂存区里明显混了多件不相关的事，提醒我改用 `/split-commits` 拆分，不要硬塞进一条。
3. 破坏性变更（API 删除、签名 / 行为不兼容）：在 message 里用 `type!:` 或加 `BREAKING CHANGE:` 脚注说明，并**停下来向我确认**这确实是破坏性改动——这类改动我要亲自把关。
4. 把拟定的 commit message 展示给我（type、scope、描述，必要时正文 / 脚注），等我确认。
5. 我确认后：`git commit`（只提交已暂存内容；除非我要求，不额外 `git add`）。
6. commit message 里**不要**加 "Generated by Claude"、co-author 之类的尾注。
7. `.husky/commit-msg` 钩子会用 commitlint 校验格式；若被拦下，把报错给我并据此修正 message，**不要用 `--no-verify` 绕过钩子**。
8. 未经我确认不要提交。
