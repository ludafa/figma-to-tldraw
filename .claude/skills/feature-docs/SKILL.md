# 功能文档的写法

文档按**功能模块**组织，思路和 skill 一样：渐进式展开。

1. `apps/docs/README.md`：总索引，每个模块一行（名称、管什么、施工日期、状态），下面还有一张"按时间"表。由 `pnpm docs:index` 从各模块头部生成，**不要手改**。
2. `apps/docs/<module>/README.md`：模块入口。frontmatter 是给索引用的元数据，正文是概要、关键决定和本目录的文件说明。
3. 模块里的 `product.md`、`tech.md`、`plan.md`、`verification.md`、`probe-*.md`：原文，按需打开。

这样人能按功能直接找到目录，模型先读索引和模块入口，只在需要时打开原文。所以每一层都要写清楚"下一层里有什么"，读者才能判断要不要往下点。

动笔前先看 `apps/docs/README.md` 和一个写得完整的模块（如 `apps/docs/lint-format/`），对齐语气和颗粒度。`references/templates.md` 有每种文件的骨架。

## 1. 模块和文件

```
apps/docs/
  README.md                 # 生成的总索引
  <module>/                 # 目录名 = 功能模块，小写英文短横线，如 auth、lint-format
    README.md               # 模块入口（必有）
    product.md              # 产品设计：做什么、为什么、怎么算成功
    tech.md                 # 技术实现：怎么做
    plan.md                 # 施工计划：按日期分节的施工记录
    verification.md         # 验证方案：测试清单 + 各次实际结果
    probe-<主题>.md         # 可选：可行性调研，只回答"能不能做"
```

- **新功能先判断归属**：属于已有模块就在那个模块里追加；是新的独立功能才新建目录。一个功能跨几个模块时，放在主要模块，其它模块在 README 的"相关模块"里链过去。
- 没内容的文件不建。小功能可以只有 `README.md` + `tech.md`。
- 文件名里不出现日期；日期只出现在 frontmatter 的 `changes`、章节标题的标注和 `plan.md` 的日期小节里。

## 2. 模块入口 README.md

```markdown
---
name: lint-format
title: 代码规范与格式化
description: 全仓库一套 Oxlint + Oxfmt（.oxlintrc.json / .oxfmtrc.json）……；改 lint 规则、格式化选项、编辑器集成或排查 pnpm lint 报错时来读。
changes: [2026-10-21]
status: 已上线
code:
  - .oxlintrc.json
  - .oxfmtrc.json
---

# 代码规范与格式化

<概要 3～6 句>

## 关键决定

- <一句结论>（2026-10-21，见 [tech.md §1](tech.md#…)）

## 文件

| 文件 | 内容 |

## 相关模块
```

- `description` 最重要：它进总索引，决定读者会不会点进来。写"管什么 + 什么时候该来读"，带上关键名词（文件名、命令、函数名、技术名）。
- `changes`：这个模块施工过的日期，`YYYY-MM-DD`，升序。一次施工（`plan.md` 里的一个日期小节）记一个日期，就是那个小节标题开头的日期。
- `status`：`设计中`（只有文档）/ `开发中`（施工计划里有没完成的阶段）/ `已上线`。
- `code`：主要代码位置，方便从文档跳到代码。`已上线` 的模块会检查这些路径都存在，改名或删文件时同步改这里。
- 改完头部运行 `pnpm docs:index`，把重新生成的 `apps/docs/README.md` 一起提交。`pnpm lint` 会检查索引是否最新。

## 3. product.md / tech.md：写"当前状态"

- 按主题组织，描述**现在**是什么样，不按时间顺序堆。章节标题标出引入的日期：`## 3. 截图兜底（2026-07-19）`，后来改过的写 `（2026-07-19，2026-10-21 修订）`。
- 后来的施工改了已有行为：直接改写相关章节，更新日期标注，并在原位置留一行 `> 2026-07-19 → 2026-10-21 修订：原来 X，现在 Y。理由：……`。不要把旧决定悄悄删掉，以后有人会问"当初为什么不这样"。
- 后来的施工加了一块功能：在文档**末尾追加**新章节，标题带日期。编号规则见下面"章节编号只增不改"。
- 新建 product.md 时以 `## 范围与非目标`、`## 成功标准` 收尾；新建 tech.md 时以 `## 风险`（`| 风险 | 应对 |`）收尾，未验证的假设也列进风险表。以后追加的章节排在它们后面，新的风险、非目标、成功标准仍然写回原来那一章。
- 设计阶段（status 为设计中）一般先写 product.md 的问题、行为、非目标，再写 tech.md。用户只要"技术方案"时可以先写 tech.md，但非目标和成功标准要跟用户确认后补上。
- 纯工具链、基础设施类模块（构建、lint、提交流程）可以没有 product.md；"开发者看到的行为"放进 tech.md 开头即可。

### 章节编号只增不改

代码注释用 `See apps/docs/<模块>/<文件>.md §<编号>` 引用文档（见 `CLAUDE.md`「代码注释」）。编号一变，引用就会指错地方。所以：

- **已有的章节一律不重新编号**，哪怕顺序看起来不顺、编号不连续，或者"风险"不再是最后一章。
- **新功能的章节追加在文档末尾**，编号取当前最大的一级编号 + 1：已有 `## 1.`～`## 7.`，新功能就是 `## 8. 类型感知规则（2026-11-02）`，放在 `## 7. 风险` 后面。
- 给已有章节补小节时，加在这一章的末尾，编号取这一章最大的小节号 + 1（已有 3.1～3.4 就加 3.5），不要插在中间。
- 章节过时了也不删编号：改写内容，或者留下标题、写一行 `> YYYY-MM-DD 起不再使用，见 §N。`，让旧引用还能找到去向。
- 改标题文字可以，代码引用只认编号；但文档之间按标题文字生成的锚点（如 `tech.md#1-选型2026-10-21`）会跟着变。改完跑 `pnpm docs:check-refs`：它检查代码引用、同一文档里编号不重复（两个分支各加了同一个编号时，后合并的一方改成下一个号）、文档链接和锚点。

## 4. plan.md：按日期记录施工

施工计划是历史记录：每次施工一个 `## YYYY-MM-DD（分支 …）` 小节（日期取开始那天，跨几天可以写成 `2026-09-24～09-26`），下面按阶段写。写计划时先填"文件"和"状态"，**每完成一个阶段就回来更新**，把计划改成实际发生的事。

```markdown
## 2026-11-02（分支 `feat/type-aware-lint`）

### 阶段 1：<名称>

- 文件：`apps/server/src/…/a.ts`（新）、`…/b.ts` + 测试。
- 状态：⬜ 未开始 / 🟡 进行中 / ✅ 完成（2026-11-03）
- 实际改动：……
- 检查：`pnpm lint`、`pnpm typecheck`、`pnpm test`（新增 N 条，测什么；共 M 条通过）的结果。
- 偏差：计划外的改动和原因（没有就不写）。
```

- 每个阶段都能单独提交、单独验证。第一个阶段常是"阶段 0：预研"，最后一个是"验证方案"。
- 计划外的工作插成 `阶段 5b`、`5c`，标题注明来源，如"（用户试用发现，计划外）"。修 bug 的阶段写"现象 → 原因 → 实际改动 → 检查"。
- 一次施工动了几个模块：阶段写在主要模块的 plan.md 里，其它模块在同日期小节下留一行指过去。

## 5. verification.md

1. `## 1. 自动测试`：`| 测试文件 | 测什么 | 日期 |`，描述当前状态（加了测试就更新对应行）。没有单测的模块写清楚靠哪些命令兜底。
2. `## 2. 端到端检查`：`| 检查 | 预期 | 日期 |`，指跑通整条流程的命令或操作，如 `pnpm bootstrap`、`pnpm build`、dev server 返回 200。
3. `## 3. 手动验收清单`：编号列表，每条"操作 → 应该看到什么"，具体到命令、文件或按钮。只保留对当前行为仍然成立的条目，所以它同时是回归清单。
4. `## 4. 各次实际结果`：每次施工一个 `### YYYY-MM-DD`，如实写本机各命令的结果、测试条数、实测耗时、手动验收哪些通过哪些没做、过程中发现并修复的问题。有 CI 之后再写 run 链接和提交号。

## 6. 写作风格

这些文档读起来像一个工程师写给同事的说明，不像 PPT。

- **大白话，短句。** 说"保存文件后 lint 报错，还得自己再跑一遍格式化"，不说"开发者存在工具链割裂痛点"。必须用的英文 API 名放反引号里。
- **先结论，后理由。** 每个决定都跟一句理由，没选的方案也说明为什么不选（用"方案 | 结论"表格，✅/❌）。
- **写出处。** 用户拍板的决定加括号标注：（用户拍板）（用户确认）（用户补充）（用户追加）（用户试用发现）。以后就知道哪些能改、哪些要先问。
- **数字要具体，带单位，注明是不是实测**："全量 lint 约 0.12 秒（实测，Node 26，81 个文件）"。没测过的写"未验证"。
- **写出代码位置。** 涉及的代码写路径和符号：`apps/server/src/middleware/auth.ts` 的 `requireAuth`；新文件标"（新）"。
- **文档是唯一的说明来源。** 代码注释不重复文档内容，只写 `See apps/docs/<模块>/<文件>.md §<章节>`（规则见 `CLAUDE.md`「代码注释」）。所以章节编号只增不改（见上面"章节编号只增不改"）；把代码里原有的说明性注释挪进文档时，内容要完整搬过来，再把注释换成引用。
- 加粗只给关键句；并列信息用表格，步骤用有序列表；代码块只放接口、数据结构、配置片段和流程示意。
- 日期一律写成 `YYYY-MM-DD`。不写"本文档旨在""综上所述"这类空话。
- 文件开头：`# <模块中文名>：技术实现`，下一行 `> 相关：[模块说明](README.md) · [施工计划](plan.md) · …`（只链接存在的文件）。跨模块链接用相对路径 `../toolchain/tech.md`。

## 7. 提交

- 代码提交顺带更新受影响的文档（plan.md 的阶段状态、tech.md 里变了的细节、verification.md 的检查表），和代码放在同一个提交里，这样文档不会和代码对不上。
- 只改文档时，提交信息用 `docs: <英文短句>`，如 `docs: record the type-aware lint results`（格式规则见 `CLAUDE.md`「Git 提交约定」）。
